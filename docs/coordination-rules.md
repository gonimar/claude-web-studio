# Agent Coordination Rules

1. **Vertical delegation**: directors → leads → specialists. Complex decisions never skip a tier.
2. **Horizontal consultation**: agents on the same tier consult each other but make no binding decisions outside their domain.
3. **Conflicts** escalate to the shared parent; technical → `technical-director`, product → `product-director`.
4. **Cross-cutting changes** (API contract, DB schema, design tokens) are coordinated by the owning lead, who notifies affected leads.
5. **No unilateral edits outside your directories** without delegation.
6. **Security is cross-cutting**: `security-lead` may veto a merge on blocking findings.
7. **One collaboration protocol for all agents**: ask → propose 2–3 options with costs → the user decides → draft → explicit approval before writing files (except small additive edits within an agreed step). **The question is a choice, not a prompt for "yes"**: every consent gate and every hand-off to the next skill is one `AskUserQuestion` — the recommended action first, marked "(Recommended)", then the real alternatives (do something first · show the draft/diff · stop); the harness adds "Other". A plain-text question only when there is no alternative. **A hand-off after a detour returns to the interrupted intent**: "we were heading to X, detoured to Y — back to X (Recommended)"; a detour never overwrites the pending `Next:` in session-state. Subagents without the tool (Tier 3 specialists) return the choice to the caller instead of deciding. For a delegated step the caller's plan answer is the explicit approval for the files the plan names: the caller touches `.claude/.write-consent` after that answer and again before each `Task` batch, and anything beyond those files comes back to the caller, which asks. **The write gate has an exact order**: (1) the draft is shown in the chat message, **rendered readably** — tabular content as a markdown table (an AC matrix, a plan table, a criteria list is rendered as the table itself, never "see the plan above" and never a raw fenced dump of file text), prose as prose; the same applies to **updates**: an edit shows the resulting table or the changed rows before the question. Showing never means creating the file; (2) the "May I write `<path>`?" `AskUserQuestion`; (3) `Write`/`Edit` only after the "write" answer. Writing before the answer is a protocol violation even if reverted — "the file is already written as a draft, confirm?" is exactly the failure this order prevents. After the "write" answer, `touch .claude/.write-consent` (the consent-guard hook checks the marker; warn-only). **A document is written with `Write`/`Edit`, not with a Bash heredoc**: `cat > file <<EOF` and `python3 - <<PY` produce the same file but route around the tool the gates, the secret scan and the format checks are attached to — measured on a real day: 588 Bash calls, zero Edits, zero guard lines, and the consent marker touched 176 times with nobody to read it. The hooks now also read Bash commands, but that is a safety net for the paths a command names literally, not a licence: a path assembled from a variable is invisible to it. **One turn, one gate**: parameters (capacity, dates, names) are asked before a gate, never in the same message as one — a single "yes" must never cover a merge and a write at once; the write gate is its own message with the draft. **An open gate survives the next turn**: before asking, the skill records `Gate: <skill> <phase>: <question>` in `production/session-state/active.md` (and `Task:` names the skill), clears it after the answer; the answer to an open gate continues that skill — it is never read as a new task from `Next:`, and a session that resumes with a `Gate:` line continues there (session-start prints it). Every artifact-producing skill follows it, and after the write comes **(4) one commit gate**: offer a `docs:` Conventional Commit staging exactly the written files, on the branch git-workflow's documents lane prescribes (default branch for pipeline-wide documents; the skill names the current branch when it is a story branch).
   **The chosen option is a contract**: the answer to an `AskUserQuestion` binds the skill for the rest of the task — a rejected option is not implemented "as well", not prepared in drafts, not re-offered; an answer that does not name the gated action (a free-text "Other" naming a different task, a question back) is **not consent** — the skill closes the open gate with its own question first, then turns to the named task. `AskUserQuestion` is never used as a pause or a placeholder: when there is nothing for the user to decide, end the turn with a text line.
8. **Stack reference first**: before working, an agent reads `.claude/docs/stack-reference/<technology>.md`. If it is older than 60 days, the agent says so and suggests `/stack-update`.
9. **Catalog artifacts are produced by their commands, never inline**: work converging on a
   catalog step's artifact is handed off to that step's command (an `AskUserQuestion`), not
   authored in the main conversation — inline authoring bypasses the step's gates, templates
   and hand-offs (CLAUDE.md principle 7).
10. **Language**: reply in the conversation language set in the project's CLAUDE.md (default English); code, identifiers, file paths and commit messages stay in English.
11. **Change impact triage**: a change proposal that arrives in the conversation rather than through an approved story — the user's "let's also…", a new dependency, a contract/schema/auth change, a deployment change — is classified before code by `/impact`: architecture → `technical-director`, security → `security-lead`, product scope → `product-director`, routine → proceed. The class is claimed from evidence (the ADR, threat-model surface, contract or path glob it touches), never from how the request sounds; the verifier's verdict (`APPROVED` · `APPROVED WITH CONDITIONS` · `NEEDS ADR` · `BLOCKED`, ≤ 15 lines) is incomplete without the commands to run next, and the skill hands off to the first of them. The review mode scopes the verification (review-workflow.md § Change classes). Nothing is verified twice: a story that passed its spec and ADR gates is not re-verified file by file — `/dev-story` touches `.claude/.impact-verdict` at story start; the `impact-guard` hook (warn-only) reminds when an architecture/security path is written without a fresh marker. **Trivial text changes** — a comment, a typo, formatting, a log message or docstring, with no behavioural change — are routine whatever path they touch: no triage, no verifier (the `security-sensitive` review-before-merge still applies to the PR, not to the triage). **A musing is not a proposal**: "what if we…", "maybe…", "it would be nice…" without a decision behind it is an idea — the conversation names it as such and offers `/backlog add`; nothing is implemented, drafted or planned from it in that turn, and `/impact` sees it only after `/backlog promote`.

12. **A number in a document cites an artefact, not the session state.** Measurements, benchmark runs and verdict figures go into `docs/ops/measurements/YYYY-MM-DD-<topic>.md` — command, environment, raw output, the number — and the document (an ADR's Verification, a finding, a story's criteria) links to that file. `production/session-state/active.md` is gitignored working memory that the next session may not have: a decision whose evidence lived only there is a decision with no evidence at all, and `Notes:` grew into the only place measurements were written down.

13. **One story per session.** The parent's context is the studio's largest cost: on a 1M window a session runs for days without compaction and every request re-reads it — measured on a real week, 80 % of the spend was the parent's context, not the agents' work (contexts of 400–966 k on 85 % of requests). `/story-done` hands off to `/clear` before the next story; `/dev-story` does not start a story past 50 % context (the statusline `ctx:` share) without offering `/clear` first; a re-review after fixes starts fresh past that mark. A session that has to keep going says why in one line.

## Models

| Tier | Model | Use |
|---|---|---|
| Haiku | `haiku` | Read-and-format work without creative judgement: `/help`, `/sprint-status`, `/changelog`, a11y checklists, documentation |
| Sonnet | `sonnet` | Implementation, specifications, single-system analysis — the default |
| Opus | `opus` | Multi-document synthesis, phase gates, `/architecture-review`, `/threat-model`, `/team-*` |

New skill: Haiku if it only reads and formats; Opus if it synthesises 5+ documents with high stakes; otherwise Sonnet.
A skill's `model:` frontmatter switches the model for the whole turn, the closing hand-off included, so only the
exceptions above pin one (`/help` haiku; `/architecture-review`, `/threat-model`, `/team-*` opus); every other skill
runs on the session model. An agent's `model:` is its own and applies inside `Task`.

## Subagents

Orchestrating skills (`/team-*`, `/dev-story`) spawn subagents via `Task`. Every agent with `memory: project` writes under `.claude/agent-memory/<agent>/` (`web-studio-<agent>` in plugin mode); those files are part of the work and are committed with it (git-workflow § Agent memory), never stashed and never reverted by a later session. Independent tasks are
launched in one batch and run in parallel; results are collected before dependent phases; a
`BLOCKED` from any agent is surfaced immediately and a partial report is mandatory.
**`subagent_type` is always a studio agent** (`web-studio:<name>` in plugin mode, `<name>` in copy mode). A
generic agent — `general-purpose`, `claude`, an explore agent, anything with a model override instead of a
roster name — is not a substitute for a reviewer or a specialist: it arrives without the project's rules,
without the agent's own memory, and the audit log records no role for it. Wanting a stronger opinion changes
the *model of the studio agent*, never the agent itself.
**Commands are namespaced too**: in plugin mode every hand-off option, `Next:` line and `/help` output names `/web-studio:<command>`; copy mode names `/<command>`. A bare `/code-review` in plugin mode runs Claude Code's **built-in** skill of the same name (`/security-review` and `/simplify` exist there too): one general-purpose agent, no routing table, no `appsec-engineer` — and its findings then travel under the studio's name, which is how a security-sensitive story was closed with "sensitive paths verified by appsec-engineer" and no appsec run in the log.
**A skill runs another studio skill through the `Skill` tool** — `/web-studio:<name>` in plugin mode, `/<name>` in copy mode — and only a skill that lists `Skill` in its `allowed-tools` does so: the orchestrating skills (`/team-*`, `/hotfix`, `/incident` for its rollback or hotfix), `/dev-story` (its `/impact` detour, the `/backlog add` of Phase 6) and `/refactor --apply` (its `/impact` detour). The called skill runs with all of its own phases and gates — a parent calling it skips nothing — and its verdict comes back as text the caller reads and quotes. Skills run one after another: `‖` in a skill body means one `Task` batch of agents launched together, never two skills at once. A skill that does not list `Skill` hands off instead — a closing `AskUserQuestion` that names the command (see the namespaced hand-offs above), and the turn ends.
**Product code and tests are written by a Tier-3 engineer in every mode** — a story, the fixes after a review, a hotfix, a refactor step, a free conversation. A cut-off agent is resumed with its `Checkpoint:`, never replaced by the parent; the second cut-off splits the step; only then may the parent write, and the result says so in one line ("written by the parent: …"). The `parent-write` hook logs every code file the session writes itself (`ParentWrite` in `production/session-logs/agent-audit.log`, warn-only) and `/sprint-status` prints the count — a rule with no observer was broken from round three of a review on a real project, "not a decision, a deviation".
**A subagent has a turn budget, and running out of it is normal.** A mid-sized story in a typed language costs a specialist more turns than the default limit allows, so a truncated result is an expected outcome, not a failure of the agent: the sign is a result that stops mid-sentence, or a log with a `SubagentStart` and no matching `SubagentStop`. The caller resumes that agent with its own id and the work it had left — never spawns a second one on the same task, which starts from an empty head and redoes what the first had already done. Work is handed out in pieces a budget can hold: one layer, one file cluster, one question per call, and the result carries what the caller cannot reconstruct — decisions, surprises, numbers — not a copy of the diff, which the caller reads with `git diff`.
**A reviewer reads what it reviews**: a draft goes to the subagent as a path it can read plus a requirement to
quote back a named part of it; pasting an abbreviated draft, or a placeholder, produces a verdict about
nothing. A verdict that quotes nothing is returned once and then reported as unread, never counted.

## Skill conventions

Every studio skill follows these; a skill body names them by section instead of restating them.

- **Language** — rule 10: reply in the project's conversation language (CLAUDE.md → Language); code, identifiers, paths and commit messages stay in English.
- **Paths and names** — `<hooks>` is `.claude/hooks/` in copy mode and `${CLAUDE_PLUGIN_ROOT}/hooks/` in plugin mode; a studio agent is `web-studio:<name>` in plugin mode and `<name>` in copy mode; a command is `/web-studio:<name>` in plugin mode and `/<name>` in copy mode (§ Subagents). `<default>` is the default branch (`master` or `main`).
- **Gates** — rule 7: show the draft → "May I write `<path>`?" as one `AskUserQuestion` (Recommended first) → after the "write" answer `touch .claude/.write-consent`, then `Write`/`Edit` (the consent-guard hook checks the marker at the write; the touch comes first). Before each gate `<hooks>session-state.sh set Gate "/<skill> Phase N: <question>"`; after the answer `<hooks>session-state.sh set Gate "—"`. A subagent has no `AskUserQuestion`: consent is collected by the session that runs the skill.
- **Documents-lane commit gate** — rule 7 (4) and git-workflow § Rules: after a write, one `AskUserQuestion` offers a `docs:` commit staging exactly the written files. On the default branch when no story work is in progress. When HEAD is a story branch, name it and offer: switch to `<default>` and commit there (Recommended: `git switch <default> && git pull --ff-only origin <default>`, commit, `git switch <branch>` back) · commit here (the document rides the story's PR) · leave uncommitted. Product code never rides a `docs:` commit.
- **Another skill** — § Subagents: a skill listed in `allowed-tools: Skill` runs another studio skill through the `Skill` tool with all of its phases and gates, one after another, never inside a `Task` batch; every other skill hands off with a closing `AskUserQuestion` naming the namespaced command, and the turn ends.
- **Subagents** — § Subagents: `subagent_type` is always a studio agent; a cut-off agent is resumed with its `Checkpoint:`, a second cut-off splits the step, only then may the parent write (and says so); a reviewer quotes what it read (`Read: N/M files`).
- **CI wait** — read the workflow triggers before waiting (`push` starts a run on the branch; `pull_request` only starts one for a PR — open a draft PR then); wait with one background `gh run watch --exit-status`, never with polling, `Monitor`, `ScheduleWakeup` or an `AskUserQuestion` used as a pause; a slow queue ends the turn with one status line.
- **Verdict and next step** — the verdict is one word from the skill's vocabulary on its own line; the next step is one `AskUserQuestion` naming the namespaced command (Recommended) and the real alternatives (one exception: a `ROUTINE` from `/impact` ends with the text line `Next step: /dev-story <story>` — the work is already inside an approved story, and `/dev-story` runs `/impact` mid-flow); in plugin mode a bare `/code-review` is Claude Code's built-in review, never the studio's.
